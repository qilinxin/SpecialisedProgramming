question1:

2. Find the critical point between addition and subtraction
In the previous step, all the cats were arranged from left to right. Each cat must move X, so the only options are "original position - X" or "original position + X." To minimize the difference,
I need to find a split point k: at which all cats to the left of k move right, and at k and its right, all cats move left. My solution is to try k from 0 to n. Each time, I linearly scan the new positions
of all cats, recording the minimum and maximum values. The difference between these values is the result. The minimum value among all k is the answer.

My solution to this problem is to first define a custom node and create nodes for all nodes numbered i.
Second, create a corresponding tree based on the node, attaching node i to its parent node based on parent[i]. The subscript where parent[i] == -1 is the root.
Third, retrieve the result. If the deleted node is the root, return 0. Otherwise, perform a DFS from the root: skip the entire tree if a deleted node is encountered;

Finally, summarize the results.

question4:
Since direct traversal isn't feasible, I break the problem down. This logic is similar to the DP we used before: once each adjacent digit must differ by at least 2, the valid choices for the next
digit depend on the previous digit. So I’ll design a bitwise counter: break the upper bound n into a digit array (most-significant to least-significant). Starting from the highest digit,
I “select digits” one by one to construct all legal numbers not exceeding n, while counting along the way.
For the interval, compute count(high) and count(low-1) and subtract. During branching, the set of digits we can choose at the current position depends on whether we are tight to the upper bound . If I have not
started the number yet and choose 0, remain in the leading-zero phase and do not apply the adjacency constraint. Once started, every subsequent digit must differ from the previous digit by at least 2. When all positions
are processed, count the path only if we have started. We memoize states only when not tight (free states), so each such state is computed once. Single-digit numbers are naturally counted as jumpy.

4. What did you learn from the problem? How this problem type of problems will help you to be a better problem solver?
My common feeling about these problems is: Don't just try to force a solution right away. First, "see the problem clearly and break it down." First, identify the structure: some lend themselves to "lining up first,
then finding a split point," some naturally lend themselves to "parent pointers → building a tree one by one," some require "discarding whatever can be picked up for free first, then consuming them alternately according to the rules,"
and still others require "bitwise counting, counting all the way through." Then, transform the constraints into easily manipulated switches and states: for example, "Does it start?", "Is it stuck at the upper bound?", "What's the previous digit?",
"Deleting a node means the entire subtree is gone?", "The end is near, so you can only connect to the beginning." By incorporating these into the transitions, the code will naturally be streamlined.
In terms of approach, strive for stability: greedy where provable, scan all possible splits, and memoize any state that can be cached. Boundaries should also be considered upfront: what if the root is deleted, how to start without a quick start,
and whether leading zeros count. This way, brute-force structure becomes simpler, the thinking becomes clearer, the code becomes shorter, and testing becomes more reliable. The biggest improvement is: when I encounter unfamiliar questions in the future,
I can first look for "element + constraint + transfer", choose a convenient model (enumeration/tree/greedy/DP), and I won't panic.
